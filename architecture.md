Ниже представлена архитектура клиент-серверного приложения для проведения онлайн-уроков с совместной интерактивной доской на стеке **Python (FastAPI) + HTML5 + JavaScript**. Архитектура спроектирована так, чтобы поддерживать рисование, вставку изображений, синхронизацию действий в реальном времени и разграничение ролей (учитель / ученик).

---

## 1. Общая архитектура

Приложение строится по классической **клиент-серверной модели с двусторонним обменом через WebSocket**:

```
Браузер (Учитель) ◄──WebSocket──┐
                                ├──► FastAPI (WebSocket-сервер) ──► Хранилище состояния
Браузер (Ученик)  ◄──WebSocket──┘
```

**Клиент** — одностраничное веб-приложение на HTML5 / Vanilla JS (или с лёгкой библиотекой для Canvas). Отвечает за отрисовку доски, обработку ввода (мышь, касания, вставка изображений) и отправку событий на сервер.

**Сервер** — приложение на Python (FastAPI + Uvicorn). Управляет «комнатами» (уроками), поддерживает список подключённых участников, транслирует события между ними и хранит актуальное состояние доски.

Такая схема хорошо зарекомендовала себя в реальных проектах: FastAPI держит WebSocket-соединения, хранит состояние комнат в памяти (словарь `rooms: Dict[str, Room]`) и пересылает сообщения всем участникам, кроме отправителя, чтобы избежать эха.

---

## 2. Клиентская часть (HTML / JS)

### 2.1. Выбор библиотеки для Canvas

Для интерактивной доски с объектами (линии, фигуры, текст, изображения) рекомендуется **Konva.js**, а не «голый» Canvas или Fabric.js:

- **Konva.js** предоставляет объектную модель, систему событий с всплытием, drag-and-drop, трансформацию (поворот, масштабирование) и сериализацию. Именно она позиционируется как решение для «интерактивных приложений: редакторов,白бордов, аннотаций».
- **Fabric.js** стоит выбирать, если критична возможность **экспорта в SVG** (например, для сохранения доски в векторном формате). Konva не умеет экспортировать в SVG, так как рисует в Canvas.

Если требуется минимализм и полный контроль над каждым пикселем, можно использовать чистый Canvas 2D API, но объём кода для объектов, трансформаций и hit-testing возрастёт многократно.

### 2.2. Основные модули клиента

1. **Рендерер доски** — слой Konva (или Canvas), на котором размещаются все графические объекты.
2. **Инструменты** — кисть (свободное рисование), ластик, фигуры (прямоугольник, круг, линия, стрелка), текст, вставка изображений.
3. **Обработчик ввода** — преобразует движения мыши / касания в нормализованные координаты доски (0…1 или мировые координаты) и генерирует события `stroke_start`, `stroke_point`, `stroke_end`.
4. **WebSocket-клиент** — устанавливает соединение с сервером, отправляет локальные события и принимает удалённые. Для курсоров используется троттлинг (~20 сообщений/сек), чтобы не перегружать канал.
5. **Локальный оптимистичный рендеринг** — пользователь сразу видит свой штрих, не дожидаясь ответа сервера. Сервер не пересылает сообщение обратно отправителю.

### 2.3. Вставка изображений

Изображения **не передаются через WebSocket целиком**. Схема:

1. Клиент загружает файл через обычный `POST /upload` (multipart/form-data).
2. Сервер сохраняет файл (локально или в S3-совместимое хранилище) и возвращает URL.
3. Клиент отправляет через WebSocket событие `image_add` с этим URL и координатами.
4. Остальные участники получают событие и подгружают изображение по URL, размещая его на доске.

## 3. Серверная часть (Python / FastAPI)

### 3.1. Управление комнатами

Каждый урок — это **комната (Room)**. Сервер хранит реестр комнат и для каждой комнаты:

- набор активных WebSocket-подключений (с id, именем, цветом и ролью пользователя);
- список завершённых графических объектов (штрихи, фигуры, изображения) для «догоняющей» синхронизации опоздавших участников.

В простейшем варианте состояние хранится **в памяти процесса** (словарь). Это быстро и просто, но при перезапуске сервера история комнаты теряется. Для продакшена состояние (или его снимки) стоит периодически сохранять в БД (см. п. 5).

### 3.2. WebSocket-эндпоинт

Один WebSocket на клиента: `/ws/{room_id}?token=...`. После подключения сервер отправляет клиенту **снимок состояния (`init`)**:

```json
{
  "type": "init",
  "clientId": "u_123",
  "users": [{"id": "u_456", "name": "Анна", "role": "teacher"}],
  "objects": [ ... ],
  "userCount": 2
}
```

Далее сервер ретранслирует события между участниками комнаты. Он **не выполняет сложного разрешения конфликтов** — штрихи считаются append-only, а событие `clear` очищает доску для всех (модель last-write-wins). Для учебной доски этого обычно достаточно, так как simultaneous-рисование в одной точке — редкий сценарий.

### 3.3. Протокол сообщений (JSON)

**Клиент → Сервер:**

| Тип | Полезная нагрузка |
|---|---|
| `stroke_start` | `{strokeId, tool, color, width, point: {x, y}}` |
| `stroke_point` | `{strokeId, point: {x, y}}` |
| `stroke_end` | `{strokeId}` |
| `shape_add` | `{shapeId, shapeType, params, ...}` |
| `text_add` | `{textId, content, x, y, ...}` |
| `image_add` | `{imageId, url, x, y, width, height}` |
| `cursor` | `{x, y}` |
| `clear` | `{}` |

**Сервер → Клиент:**

| Тип | Полезная нагрузка |
|---|---|
| `init` | снимок состояния комнаты (unicast) |
| `user_joined` / `user_left` | данные пользователя |
| `stroke_start` / `stroke_point` / `stroke_end` | те же данные + `id` отправителя |
| `shape_add` / `text_add` / `image_add` | те же данные + `id` отправителя |
| `cursor` | `{id, x, y, name, color}` |
| `clear` | `{id}` |

Все широковещательные сообщения (кроме `init`) уходят **всем, кроме отправителя** — отправитель уже отрисовал действие локально.

## 4. Синхронизация состояния: практический выбор

Для онлайн-доски на уроке **не обязательно** внедрять CRDT или Operational Transformation. Эти подходы нужны, когда несколько пользователей одновременно редактируют **один и тот же объект** (например, текст в общей строке). Для рисования и добавления фигур достаточно модели **append-only + last-write-wins**:

- каждый новый штрих / фигура / изображение добавляется в конец списка;
- `clear` сбрасывает список;
- порядок объектов сохраняется, если сервер присваивает каждому объекту монотонный `seq`.

Если в будущем потребуется **совместное редактирование текста** или **перемещение одного объекта двумя пользователями одновременно**, можно перейти на **CRDT** (например, библиотека Automerge). Исследования показывают, что CRDT хорошо подходят для白бордов и позволяют отказаться от сложной серверной логики разрешения конфликтов. Однако для первой версии это избыточно.

## 5. Хранение данных и персистентность

| Компонент | Назначение | Рекомендация |
|---|---|---|
| **In-memory (dict)** | Активное состояние комнат | На старте; самый быстрый вариант |
| **SQLite / PostgreSQL** | Сохранение снимков доски после урока | SQLite подходит для одного сервера; PostgreSQL — для нескольких инстансов |
| **Файловое хранилище / S3** | Загруженные изображения | Локальная папка на старте; S3-совместимое хранилище при росте |

Стратегия: во время урока состояние живёт в памяти; по событию `lesson_end` (или периодически) сервер сериализует список объектов и сохраняет в БД. При повторном входе в комнату состояние восстанавливается из БД, если в памяти его ещё нет.

---

## 6. Роли и безопасность

- **Аутентификация:** JWT-токен передаётся в query-параметре при подключении к WebSocket или в первом сообщении. Сервер проверяет подпись и извлекает `user_id` и `role` (`teacher` / `student`).
- **Разграничение прав:** проверка на сервере. Например, `clear` и `kick` разрешены только учителю. Клиентская блокировка кнопок — лишь UX, не безопасность.
- **Валидация входных данных:** Pydantic-схемы для REST и ручная проверка структуры WebSocket-сообщений. Это защищает от мусорных данных и попыток инъекций.
- **Ограничение частоты:** троттлинг курсоров на клиенте и rate-limit на сервере для сообщений (`stroke_point` не чаще 60/сек на пользователя).

---

## 7. Масштабирование (если понадобится)

Один процесс FastAPI с in-memory состоянием держит все комнаты. Когда пользователей станет много, появится необходимость в **горизонтальном масштабировании**:

1. **Redis Pub/Sub** — каждый инстанс FastAPI подписывается на каналы комнат. Событие, полученное одним инстансом, публикуется в Redis и доставляется всем инстансам, которые держат участников этой комнаты.
2. **Sticky sessions** на балансировщике — чтобы WebSocket-клиент всегда попадал на тот же инстанс (не обязательно при использовании Redis, но упрощает отладку).
3. **Вынос состояния** из памяти в Redis (с периодическим сбросом в БД) — чтобы любой инстанс мог восстановить комнату.

Для старта и среднего масштаба (до нескольких сотен одновременных уроков) достаточно одного инстанса с in-memory состоянием.

## 8. Рекомендуемая структура проекта

```
project/
├── backend/
│   ├── app/
│   │   ├── main.py              # FastAPI, CORS, монтирование статики
│   │   ├── config.py            # настройки (JWT secret, лимиты)
│   │   ├── models/
│   │   │   └── schemas.py       # Pydantic-схемы сообщений
│   │   ├── services/
│   │   │   ├── room_manager.py  # реестр комнат, подключения
│   │   │   └── storage.py       # сохранение снимков в БД / файлы
│   │   └── api/
│   │       ├── ws.py            # WebSocket-эндпоинт
│   │       └── upload.py        # POST /upload для изображений
│   └── requirements.txt
└── frontend/
    ├── index.html               # разметка доски и панели инструментов
    ├── js/
    │   ├── main.js              # инициализация, WebSocket-клиент
    │   ├── board.js             # Konva-сцена, объекты
    │   ├── tools.js             # кисть, фигуры, текст, изображения
    │   └── sync.js              # отправка / приём событий
    └── css/style.css
```

Эта структура повторяет проверенный подход из открытых проектов: разделение на `models` (валидация), `services` (логика комнат и хранения) и `api` (транспорт).

## 9. Ключевые архитектурные решения (резюме)

| Решение | Выбор | Обоснование |
|---|---|---|
| Транспорт реального времени | **WebSocket** | Двусторонняя низкая задержка, стандарт для collaborative-приложений |
| Backend-фреймворк | **FastAPI (async)** | Нативная поддержка WebSocket, высокая производительность, Pydantic-валидация |
| Canvas-библиотека | **Konva.js** (или чистый Canvas) | Объектная модель, события, трансформации — всё для интерактивной доски |
| Синхронизация | **Append-only / last-write-wins** | Достаточно для рисования; CRDT/OT — задел на будущее |
| Состояние | **In-memory + периодический снимок в БД** | Простота и скорость на старте, персистентность после урока |
| Изображения | **REST upload + URL через WebSocket** | Не раздувает WebSocket-канал |

Такая архитектура позволяет запустить рабочий прототип за минимальное время и оставляет понятные точки роста: добавление CRDT для текста, Redis для масштабирования, S3 для изображений.
