Ниже — практический план реализации онлайн-доски для уроков на стеке **FastAPI + HTML/JS (Konva.js)**. План разбит на этапы с deliverables и критериями готовности. Оценка ориентировочная для **1 fullstack-разработчика**; backend и frontend можно частично вести параллельно.

## 0. Цель MVP и границы

> **✅ Этап 0 закрыт (решения согласованы):**
> - Объём итерации: весь MVP сразу (этапы 2–8), UI на русском.
> - Аутентификация: cookie-сессии и учётные записи (ученик/учитель/администратор); роль и статус проверяются в БД. Исторически было JWT + код учителя — заменено в итерации P5.
> - Хранение: SQLite-снимки комнат + in-memory активное состояние.
> - Инфраструктура: Docker + CI (ruff/black/pytest) сразу.
> - Технические решения (на усмотрение реализации): Konva через CDN без сборки; логическая доска **1600×900** в мировых координатах, вписывается в окно с сохранением пропорций; изображения — локальная папка `uploads/`; валидация WS-сообщений Pydantic-схемами.

**В MVP входит:**
- Комната урока по `room_id`.
- Подключение учителя и ученика по WebSocket.
- Совместное рисование кистью, ластиком, фигуры, текст.
- Вставка изображений через загрузку файла.
- Курсоры участников.
- Очистка доски (только учитель).
- Базовые роли `teacher` / `student`.
- Сохранение снимка доски после урока.

**Вне MVP (задел):**
- CRDT/OT для одновременного редактирования текста.
- Запись видео/аудио.
- Чат, файлы, домашние задания.
- Масштабирование через Redis Pub/Sub.

## 7. Этап: Аутентификация и роли (3–4 дня)

> **✅ Реализовано.** JWT (HS256, TTL из `.env`) выдаётся `POST /api/login`; код учителя проверяется через `hmac.compare_digest`. Токен проверяется при WS-подключении и сверяется с комнатой. Права на сервере: `clear`, `object_delete`, `kick` — только учитель; `object_update` — автор или учитель. Rate-limit по категориям. UI скрывает недоступные действия, но безопасность обеспечивает сервер.

**Задачи:**

- Роли `teacher` / `student`.
- Серверная проверка прав: `clear`, удаление объектов, кик — только учитель.
- Ограничение доступа к комнате по токену.
- Rate-limit на сообщения.

**Deliverable:** ученик не может очистить доску; учитель может.

## Критерии готовности MVP

1. Учитель и ученик подключаются к одной комнате по ссылке.
2. Оба видят штрихи, фигуры, текст и изображения друг друга с задержкой < 200 мс в локальной сети.
3. Курсоры отображаются.
4. Учитель может очистить доску; ученик — нет.
5. При переподключении состояние восстанавливается.
6. Изображения загружаются и видны всем.
7. После урока снимок сохраняется.
8. Есть E2E-тест основного сценария.
9. Приложение развёрнуто по HTTPS.

## Риски и меры

| Риск | Мера |
|---|---|
| Задержки при частых `stroke_point` | Троттлинг точек, батчинг, сжатие координат |
| Конфликты при одновременном рисовании | Модель append-only, last-write-wins; CRDT — пост-MVP |
| Большие изображения | Лимит размера, ресайз на клиенте/сервере |
| Потеря состояния при рестарте | Периодические снимки в БД |
| Масштабирование | Redis Pub/Sub — при росте нагрузки |
| Безопасность | JWT, серверные проверки ролей, rate-limit, валидация загрузок |

Такой план позволяет быстро выйти на рабочий MVP и оставляет понятные точки роста: CRDT для текста, Redis для масштабирования, S3 для файлов.

### Критерии готовности итерации

1. `pytest`, `ruff`, `black` — зелёные; E2E-набор проходит на двух браузерах и мобильном viewport.
2. Текст редактируется, объекты масштабируются и поворачиваются у всех участников.
3. Два инстанса приложения с общим Redis видят объекты и участников друг друга.
4. Изображения работают через S3-совместимое хранилище (SeaweedFS); локальный режим сохранён.
5. `/metrics`, JSON-логи, Sentry и `/health/ready` работают; Caddy-конфиг и бэкапы описаны.
6. Страницы изолируют объекты; учитель управляет страницами и переносит учеников без потери черновика; старые комнаты мигрируют без потерь.
7. Гостевого входа нет; ученик открывает только выданные комнаты; подтверждение, блокировка и смена роли действуют на REST и WS; администратор видит все комнаты.
8. Ластик стирает только штрихи кисти (стафф/автор); блоки схемы соединяются стрелками, которые следуют за блоками; фрейм двигает прикреплённые элементы и не удаляет чужие объекты у ученика.
9. Отмена возвращает последнее личное действие (включая удаление), не затирая чужие правки; замок учителя блокирует ученику любые изменения, включая детей фрейма.
10. Картинки из буфера вставляются по `Ctrl+V`; учитель скачивает текущую страницу в PDF с пропорциями 16:9.
11. Учитель загружает PDF-презентацию, листает слайды и рисует только кистью; ученик видит
    текущий слайд и пометки, но не может рисовать, менять слайд или пользоваться инструментами;
    пометки хранятся отдельно по слайдам.
12. Масштаб и панорама доски локальны: кнопки, колесо, жесты и клавиши меняют только мой вид;
    рисование после зума попадает в правильные координаты, экспорт и resize сохраняют вид.
13. Учитель отменяет последний штрих текущего слайда презентации кнопкой и `Ctrl+Z`;
    ученик отменять не может. Панели «Страницы» и «Участники» сворачиваются и запоминают
    состояние, доска и зум не ломаются.
14. Текст рисуется одним из пяти системных шрифтов, выбор синхронизирован и отменяется;
    увеличенный холст перетаскивается мышью, а отмена работает после возврата на страницу.
15. Замок блокирует изменения любой роли; размер холста задаётся на комнату и сохраняется;
    скрытый администратор не виден ученикам ни в списке, ни курсором, и может снять невидимку.
16. Обычные страницы бесконечны и свободно панорамируются; фиксированный лист включается
    на странице, PDF идёт по границам контента, презентация занимает весь слайд.
17. Ластик удаляет любые доступные элементы, `Ctrl+Z` работает в любой раскладке,
    а лассо выбирает, двигает и удаляет группу с одной отменой.
18. Панель листания презентации стоит ниже слайда; учитель задаёт цвет холста
    страницы, ученики видят его, цвет переживает перезагрузку и попадает в PDF.
