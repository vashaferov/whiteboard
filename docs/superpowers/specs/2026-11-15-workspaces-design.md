# Воркспейсы внутри комнаты — дизайн

Дата: 2026-11-15
Статус: предложен, ожидает утверждения

## 1. Зачем

Сейчас комната — это одна доска. На уроке нужны несколько независимых страниц:
учитель готовит несколько досок, ученики работают на своей странице, а учитель
может переключить конкретного ученика, нескольких или всех на свою текущую
страницу.

## 2. Цели

- В комнате несколько воркспейсов (страниц), у каждого своё содержимое.
- Список страниц видят все участники и обновляют его в реальном времени.
- Создавать, переименовывать, удалять и менять порядок страниц может только учитель.
- Каждый участник переключает страницу сам; переключение одного не меняет
  страницу у остальных.
- Учитель может «притянуть» одного, нескольких или всех учеников на свою
  текущую страницу. Притянутые остаются там после переключения учителя.
- Старые комнаты и снимки открываются с одной страницей «Страница 1» без потери
  объектов.

## 3. Не-цели

- Перемещение объектов между страницами.
- Автоматическое следование учеников за учителем.
- Показ в списке участников, кто на какой странице.
- Миниатюры страниц, drag-and-drop сортировка, копирование страниц.
- Права на отдельные страницы (все страницы комнаты доступны всем её участникам).
- Изменение CRDT-модели: по-прежнему last-write-wins.

## 4. Ограничения

- Существующий протокол и клиент: события объектов не содержат страницу.
- Снимки SQLite и состояние Redis привязаны к комнате целиком.
- Redis — опциональный режим для нескольких инстансов.
- Вёрстка уже адаптивная; панель участников скрывается на ширине меньше 900 px.
- Максимум 50 страниц на комнату, имя — 1…60 символов после trim.
- Таймаут подтверждения переноса `workspace_move_timeout_seconds` — 2 с.
- Лимит объектов `max_objects_per_room` остаётся общим на комнату.

## 5. Рассмотренные подходы

### A. `workspaceId` на объектах (выбран)

Объекты комнаты остаются одним плоским списком, у каждого появляется
`workspaceId`. У комнаты — упорядоченный словарь страниц. Broadcast фильтрует
получателей по их текущей странице.

Плюсы: минимальные изменения существующего конвейера объектов, простая миграция
старых снимков, тесты продолжают работать с плоским `room.objects`.

Минусы: изоляция страниц держится на фильтрах, нужны тесты на протечки;
`seq` и лимит объектов общие на комнату.

### B. Полноценный класс `Workspace`

У каждой страницы свои `objects`, `index`, `seq`, отдельные ключи Redis.

Плюсы: чистая изоляция, отдельные лимиты и последовательности.

Минусы: переписать обработчики, `RoomManager`, Redis и значительную часть
тестов; сложнее миграция.

### C. Воркспейс как отдельная комната

Составной id, свой канал, поверх — каталог страниц.

Плюсы: максимальная изоляция.

Минусы: presence, «притянуть» и список участников ходят между комнатами;
неоправданная инфраструктурная сложность.

Выбран **A**: нужное поведение достигается заметно дешевле, а риск утечек
закрывается тестами на изоляцию, очистку, удаление и переключение.

## 6. Модель данных

### Комната

```python
Room:
    workspaces: dict[str, dict]   # id -> {"id", "name", "position"}
    objects: list[dict]           # все объекты комнаты, у каждого workspaceId
    index: dict[str, dict]        # id -> object
    seq: int                      # общий на комнату
```

`ConnectedUser` получает `workspace_id`.

Страницы сортируются по `position`; позиции нормализуются в `0..n-1` после
создания, удаления и сортировки.

### Идентификаторы и имена

- Страница по умолчанию: id `ws_default`, имя `Страница 1`.
- Новая страница: `ws_<uuidhex>`, имя по умолчанию — следующий свободный
  `Страница N`.
- Имя: trim, 1…60 символов; пустое имя отклоняется.

### Инварианты

- В комнате всегда есть хотя бы одна страница.
- Каждый объект имеет `workspaceId`, указывающий на существующую страницу.
- При загрузке объекта с отсутствующим или неизвестным `workspaceId` он
  попадает на первую страницу.
- Страницу можно удалить только если она не последняя.
- Объект нельзя изменить или удалить, находясь на другой странице.

## 7. Права

В `Permissions` добавляется `canManageWorkspaces` (только учитель).
«Притягивание» использует существующий `canManageUsers` (только учитель).
Переключение своей страницы доступно всем.

Сервер проверяет права на каждое изменяющее сообщение, независимо от UI.

## 8. Протокол

### Клиент → сервер

| Сообщение | Поля | Права |
|---|---|---|
| `workspace_switch` | `workspaceId` | все |
| `workspace_create` | `name?` | учитель |
| `workspace_rename` | `workspaceId`, `name` | учитель |
| `workspace_delete` | `workspaceId` | учитель |
| `workspace_reorder` | `workspaceIds: list[str]` | учитель |
| `workspace_pull` | `clientIds: list[str]`, `all: bool` | учитель |
| `workspace_move_ack` | `requestId` | притянутый ученик |

`workspace_pull` требует ровно один режим: либо `all=true`, либо непустой
`clientIds`. Список целей — до 100 уникальных id. Притягиваются только ученики
этой комнаты; отсутствующие и учителя пропускаются. Если не найдено ни одной
валидной цели — ошибка `user_not_found`.

`workspace_reorder` должен содержать ровно все id комнаты без дублей; иначе
`invalid_message`.

Все сообщения объектов, курсоров и `clear` могут необязательно содержать
`workspaceId`; обновлённый клиент всегда его отправляет. Если поле присутствует
и не совпадает с текущей страницей пользователя, сервер отклоняет сообщение с
`stale_workspace` — так запоздавшее событие не попадёт на чужую страницу.

### Сервер → клиент

| Событие | Поля | Кому |
|---|---|---|
| `init` | `workspaces`, `workspaceId`, `objects` текущей страницы | подключающемуся |
| `workspace_created` | `workspace`, `by` | всем |
| `workspace_renamed` | `workspaceId`, `name` | всем |
| `workspace_deleted` | `workspaceId`, `fallbackId` | всем |
| `workspace_reordered` | `workspaceIds` | всем |
| `workspace_state` | `workspaceId`, `objects`, `stateVersion` | одному участнику |
| `workspace_moved` | `workspaceId`, `name`, `by` | притянутому ученику |
| `workspace_prepare_move` | `requestId`, `workspaceId`, `name`, `by` | притянутому ученику |
| `cursor_remove` | `id`, `workspaceId` | зрителям старой страницы |

Все события объектов (`stroke_*`, `shape_add`, `text_add`, `image_add`,
`object_update`, `object_transform`, `text_update`, `object_delete`, `clear`,
`cursor`) получают поле `workspaceId`.

`init` отдаёт только объекты текущей страницы; клиент не получает содержимое
остальных страниц до переключения.

### Восстановление страницы при переподключении

WebSocket принимает необязательный query-параметр `workspace`. Если id
существует в комнате — пользователь начинает на нём, иначе на первой странице.
Клиент хранит текущий `workspaceId` в `sessionStorage` и передаёт его при
переподключении и reload.

## 9. Поведение сервера

### Переключение своей страницы

1. Завершить активные штрихи пользователя на старой странице и разослать
   `stroke_end` зрителям старой страницы.
2. Убрать курсор со старой страницы событием `cursor_remove`.
3. Сменить `user.workspace_id`.
4. Отправить пользователю `workspace_state` с объектами новой страницы.

События объектов, пришедшие после переключения, сервер относит к новой странице:
он штампует их текущим `workspace_id` пользователя. Клиент на время переключения
блокирует ввод и буферизует события новой страницы до `workspace_state`.

### Создание

- Проверить лимит 50 страниц.
- Добавить страницу в конец, сохранить и разослать `workspace_created`.
- Создатель автоматически переключается на новую страницу (получает
  `workspace_state`); остальные остаются на своих.

### Переименование

- Проверить имя, обновить метаданные, разослать `workspace_renamed`.
- Текущая страница участников не меняется.

### Сортировка

- Проверить, что прислан ровно набор id комнаты.
- Присвоить позиции по порядку списка, разослать `workspace_reordered`.

### Удаление

- Запретить удаление последней страницы (`last_workspace`).
- Удалить все объекты этой страницы и её метаданные.
- Определить `fallbackId` — первую оставшуюся страницу.
- Всем, кто был на удалённой странице (включая учителя), отправить
  `workspace_deleted`, затем `workspace_state` с fallback-страницей.
- Активные штрихи на удалённой странице отбрасываются.
- Остальным разослать `workspace_deleted` без смены страницы.

### Притягивание

1. Учитель отправляет `workspace_pull`; целевая страница — его текущая.
2. Сервер выбирает учеников комнаты по объединённому списку участников
   (локальные + presence из Redis): одного, список или всех. Учителя и
   отсутствующих пропускает; если валидных целей нет — `user_not_found`.
3. Локальным ученикам сервер отправляет `workspace_prepare_move` с `requestId`,
   целевой страницей и именем. Для учеников на других инстансах событие
   публикуется в Redis, и каждый инстанс готовит своих локальных учеников.
4. Клиент ученика по `workspace_prepare_move`:
   - фиксирует открытый текст (`text_add`/`text_update` на старой странице);
   - завершает активный штрих (`stroke_end`), незавершённый preview фигуры
     отбрасывает;
   - отправляет `workspace_move_ack` с тем же `requestId`.
5. Сервер по ack завершает серверные штрихи, убирает курсор со старой страницы,
   меняет `workspace_id`, отправляет `workspace_moved` и `workspace_state`.
6. Если ack не пришёл за `workspace_move_timeout_seconds` (по умолчанию 2 с),
   сервер выполняет перенос принудительно. Поздний ack игнорируется.
7. Учитель и остальные ученики не меняют страницу.

Притянутый ученик остаётся на странице после переключения учителя и может сам
переключиться обратно.

### Сохранение черновика при переносе

Двухфазный перенос нужен именно для того, чтобы не потерять текст, набранный в
момент команды учителя. Клиент не блокирует ввод до получения
`workspace_prepare_move`; получив его, он:

1. Закрывает редактор и отправляет накопленный текст на старой странице.
2. Завершает штрих.
3. Отправляет ack.

WebSocket сохраняет порядок, поэтому текст и `stroke_end` приходят на сервер
раньше ack. После смены страницы запоздавшие сообщения с прежним `workspaceId`
отклоняются как `stale_workspace`.

При удалении страницы двухфазность не используется: страница и её содержимое
исчезают, поэтому черновик на ней сохранять некуда. Участники сразу получают
`workspace_deleted` и `workspace_state` с fallback-страницей.

### Версия состояния

`ConnectedUser` хранит монотонный `state_version`. Каждый `workspace_state`
получает `stateVersion`; клиент применяет только состояние с версией больше
последней. Это защищает от гонки «ручное переключение против притягивания»:
запоздавшее старое состояние не откатит страницу назад.

Для операций смены страницы одного пользователя используется per-user lock,
чтобы подготовка, ack, таймаут и ручное переключение не меняли состояние
параллельно.

### Изоляция объектов

- При создании объекта сервер ставит `workspaceId = user.workspace_id`.
- При изменении/удалении проверяет, что объект существует и его `workspaceId`
  совпадает с текущей страницей пользователя; иначе `unknown_object`.
- Broadcast объекта/курсора отправляется только участникам с тем же
  `workspaceId`.
- `clear` очищает только текущую страницу учителя.
- Курсоры видны только на общей странице; при уходе пользователя со страницы
  рассылается `cursor_remove`.

### Активные штрихи

Штрих создаётся с `workspaceId`. При переключении, притягивании или удалении
страницы активные штрихи завершаются на своей странице (кроме штрихов на
удаляемой странице — они отбрасываются), чтобы не потерять линию и не отправить
её на чужую страницу.

## 10. Хранение

### SQLite

В `room_snapshots` добавляется колонка `workspaces TEXT NOT NULL DEFAULT '[]'`.
Миграция выполняется через `PRAGMA table_info` + `ALTER TABLE`.

`Snapshot` получает `workspaces`. Сохраняются:

- `objects` — плоский список, у каждого объекта `workspaceId`;
- `workspaces` — JSON `[{"id","name","position"}]`;
- `seq` — общий счётчик комнаты.

При загрузке:

1. Если `workspaces` пуст — создать `ws_default`.
2. Удалить дубли/невалидные записи, нормализовать позиции.
3. Объектам без `workspaceId` или с неизвестным id выставить первую страницу.

Старые снимки читаются без отдельной команды миграции.

### Redis

Ключи комнаты:

```
<prefix>:room:<room>:workspaces   hash  id -> {"id","name","position"}
<prefix>:room:<room>:objects      hash  objectId -> object JSON (с workspaceId)
<prefix>:room:<room>:seq          string
<prefix>:room:<room>:presence     hash
<prefix>:room:<room>:events       pub/sub
```

- `workspace_created/renamed/reordered` обновляют hash и публикуются в канал.
- `workspace_deleted` удаляет метаданные и поля объектов этой страницы.
- `clear` удаляет только поля объектов текущей страницы.
- События объектов публикуются с `workspaceId`; каждый инстанс отправляет их
  только своим пользователям на этой странице.
- `workspace_pull` публикуется как событие с `all` или списком `clientIds`;
  каждый инстанс готовит своих учеников через `workspace_prepare_move`, ждёт
  ack локального клиента и применяет перенос.

### Приоритет Redis и SQLite

Redis — живой источник состояния, SQLite — холодное восстановление.

1. Комната загружает снимок SQLite.
2. Если в Redis есть хотя бы один из ключей состояния комнаты
   (`workspaces`, `objects`, `seq`), Redis считается авторитетным и заменяет
   страницы, объекты и `seq` из снимка. Отсутствующий hash страниц при наличии
   объектов означает старое состояние: создаётся `ws_default`, объекты
   привязываются к нему.
3. Если Redis пуст, загруженный снимок засевается в Redis: hash страниц, hash
   объектов и `seq`. Это делает первый стартовавший инстанс источником для
   остальных и не даёт им создать второй `ws_default`.
4. Объекты с неизвестным `workspaceId` при восстановлении привязываются к первой
   странице; исправление записывается обратно в Redis.

## 11. Клиент

### Состояние

```js
state.workspaces = [];          // [{id, name, position}]
state.workspaceId = null;
state.pendingWorkspaceId = null;
state.pendingEvents = [];       // события новой страницы до workspace_state
state.stateVersion = 0;         // последняя применённая версия состояния
state.moveRequestId = null;     // активный workspace_prepare_move
state.selectedStudentIds = new Set();
```

### Панель страниц

Слева от доски — панель «Страницы»:

- список страниц с номером и именем, активная подсвечена;
- клик по странице — `workspace_switch`;
- у учителя: кнопка «+ Страница», переименование, удаление, стрелки вверх/вниз;
- у ученика только список и переключение.

На ширине меньше 900 px панель становится горизонтальной полосой над доской;
панель участников, как и раньше, скрыта.

### Притягивание

В панели участников у учителя:

- чекбокс у каждого ученика;
- кнопка «К себе» для выбранных;
- кнопка «Всех к себе».

Свои строки и строки других учителей не выбираются. После отправки выделение
очищается. Ученик получает `workspace_moved` (toast) и `workspace_state`.

### Переключение и буферизация

При клике по странице:

1. Завершить открытый текст и активный штрих.
2. `state.pendingWorkspaceId = target`, `state.ready = false`, ввод на доске
   заблокирован.
3. Отправить `workspace_switch` с целевой страницей. Все события объектов
   содержат `workspaceId` страницы, на которой они созданы.

События объектов с `workspaceId === pendingWorkspaceId` складываются в
`pendingEvents`. На `workspace_state`:

1. Если `stateVersion` не больше уже применённой — состояние игнорируется.
2. `board.setObjects(objects)`, очистить курсоры и выделение.
3. Установить `workspaceId`, `pendingWorkspaceId = null`, сохранить
   `stateVersion`.
4. Применить буферизованные события (операции идемпотентны: повторный add
   игнорируется, transform с теми же данными безвреден).
5. `state.ready = true`, разблокировать ввод, обновить панель и сессию.

События старой страницы после переключения игнорируются.

При server-initiated переносе (`workspace_prepare_move`) клиент:

1. Ставит `state.moveRequestId`, блокирует переключение страниц и ввод.
2. Фиксирует открытый текст и завершает штрих на старой странице.
3. Отправляет `workspace_move_ack`.
4. Ждёт `workspace_moved` + `workspace_state`; дальнейшая логика та же.

`workspace_deleted` для текущей или ожидаемой страницы сразу переводит клиент в
ожидание `workspace_state` для `fallbackId`; редактор закрывается без сохранения,
потому что страница удаляется.

### События

- `workspace_created` — добавить в список.
- `workspace_renamed` — обновить имя.
- `workspace_reordered` — переставить список.
- `workspace_deleted` — убрать страницу; если она текущая/ожидаемая, ждать
  `workspace_state` для `fallbackId`.
- `workspace_moved` — toast и ожидание `workspace_state`.
- `cursor_remove` — удалить курсор.

## 12. Ошибки и крайние случаи

- Переключение на несуществующую страницу — `workspace_not_found`, состояние не
  меняется.
- Создание сверх лимита — `workspace_limit`.
- Удаление последней — `last_workspace`.
- Переименование в пустое/длинное имя — `invalid_message`.
- Сортировка с чужими/пропущенными id — `invalid_message`.
- Притягивание без валидных учеников — `user_not_found`.
- Ученик без прав на создание/удаление/притягивание — `forbidden`.
- Объект с чужой страницы — `stale_workspace`/`unknown_object`; состояние не
  меняется.
- Удаление страницы, на которой идёт штрих — штрих отбрасывается.
- Переключение во время открытого текстового редактора — текст фиксируется до
  отправки переключения.
- Притягивание во время набора текста — текст фиксируется на старой странице до
  ack; при таймауте перенос всё равно происходит, черновик может потеряться.
- Поздний `workspace_move_ack` после таймаута или нового запроса игнорируется.
- Отключение ученика во время подготовки — перенос отменяется по таймауту.
- Старый снимок без страниц — автоматическая миграция в `Страница 1`.

## 13. Тестирование

### Backend unit/integration

- `init` содержит `workspaces`, `workspaceId` и только объекты текущей страницы.
- Старая комната без страниц получает `ws_default`.
- Создание/переименование/сортировка/удаление: права, события, лимит, последняя
  страница, fallback при удалении.
- Изоляция объектов: добавление, transform, delete, clear, курсоры.
- Переключение: `workspace_state`, завершение штрихов, неизвестная страница.
- Притягивание одного, нескольких, всех; не затрагивает учителя и других
  учеников; не-ученики пропускаются.
- Двухфазный перенос: prepare → текст/штрих → ack → moved/state; перенос без ack
  по таймауту; поздний ack игнорируется.
- Притягивание между инстансами по объединённому roster: готовятся только
  локальные ученики, presence другого инстанса не двигается дважды.
- Снимок SQLite: roundtrip страниц, миграция старого снимка.
- Redis: метаданные страниц, изоляция объектов, удаление/clear, pull между
  инстансами, fallback старого состояния, приоритет Redis над SQLite и засев
  пустого Redis из снимка.
- Обновить существующие тесты под новое поле `permissions` и `init`.

### E2E (Playwright)

1. Учитель создаёт страницу, ученик видит её в списке.
2. Учитель рисует на странице 2; ученик на странице 1 не видит объект; после
   переключения видит.
3. Переименование и сортировка отражаются у ученика.
4. Учитель притягивает одного ученика; тот переключается, остальные нет.
5. «Всех к себе» переключает всех учеников.
6. Ученик печатает текст, учитель притягивает его: текст сохраняется на старой
   странице, ученик оказывается на странице учителя.
7. Удаление страницы переводит находящихся на ней на первую.
8. Reload восстанавливает список и текущую страницу.
