# Элементы доски: картинки, ластик, блок-схемы и фреймы — дизайн

Дата: 2026-11-16. Итерация после «учётных записей и комнат».

## 1. Зачем

Доска умеет рисовать кистью, фигуры, текст и картинки, но для урока не хватает
нескольких вещей. Картинку, вставленную учеником, нельзя сразу подвинуть: локальный объект
создаётся без автора, и перетаскивание разрешено только после перезагрузки. Ластик —
пиксельный (`destination-out`): он не удаляет объекты, оставляет «дырки», а по тонким
фигурам и тексту попасть почти невозможно. Блок-схемы приходится собирать из отдельных
прямоугольников, подписей и стрелок, которые ни к чему не привязаны. Нет фреймов —
рабочих областей, которые двигаются вместе с содержимым.

Итерация закрывает эти пробелы, не меняя модель комнат, страниц и доступа.

## 2. Цели

1. Картинки (и другие свои объекты) можно двигать сразу после создания, без перезагрузки.
2. Ластик удаляет объекты целиком при касании: штрих, фигуру, текст, картинку, блок, фрейм.
   Учитель/админ — любые, ученик — только свои; удаление синхронизируется через `object_delete`.
3. Блок-схемы: готовые блоки «процесс», «решение», «начало/конец» с подписью внутри и
   стрелки, которые прилипают к блокам и перестраиваются при их перемещении и изменении размера.
4. Фреймы: прямоугольная рабочая область с рамкой и фоном (заливка, горизонтальные линии,
   клетка). Элементы, брошенные внутрь, прикрепляются и двигаются вместе с фреймом.

## 3. Не-цели

- Пиксельное стирание (заменяется удалением объектов); старые пиксельные штрихи ластика
  продолжают отображаться, но новый ластик их не создаёт.
- Порты/точки подключения, ортогональная трассировка, подписи на стрелках, авто-раскладка схем.
- Вложенные фреймы, обрезка детей по рамке, заголовок фрейма, масштабирование детей вместе
  с фреймом.
- Копирование/вставка, undo/redo (их нет и сейчас).
- Поворот блок-схем и фреймов.

## 4. Анти-цели

- Ластик, удаляющий чужие объекты у ученика.
- Стрелка, которая «отклеивается» от блока при его перемещении.
- Фрейм, который при удалении оставляет «сирот» или молча удаляет чужие объекты у ученика.
- Новый тип объекта, дублирующий существующие `shape`/`image` без необходимости.

## 5. Ограничения

- Объекты комнаты — плоский список с `workspaceId`; страницы изолируют объекты; broadcast
  фильтруется по странице; персистентность — SQLite-снимок + Redis live-состояние.
- Валидация WS-сообщений — Pydantic; неизвестные поля запрещены (`extra="forbid"`).
- Конвас Konva.js, ванильный JS без сборки; объекты адресуются абсолютными мировыми координатами.
- Правки не должны ломать существующие снимки: старые объекты без `frameId` читаются как
  обычные; старые пиксельные штрихи ластика остаются видимыми.

## 6. Рассмотренные подходы

**Фреймы: A. Плоская модель (выбрана).** У элемента появляется `frameId`, координаты
остаются абсолютными; фрейм — объект-подложка; перемещение фрейма сдвигает детей одной
операцией на сервере. Выделение, слои, протокол и права почти не меняются; вытащенный
элемент теряет `frameId`. Минус: обрезка/масштабирование детей позже потребуют доработки.

**B. Настоящая группа.** Дети — вложенные узлы Konva с координатами относительно фрейма,
фрейм — родитель. Перемещение/масштаб бесплатны, возможна обрезка. Минус: выделение и
z-order через границы групп, обмен элементами между фреймами и протокол заметно сложнее;
для оговорённого поведения (без обрезки и масштабирования детей) выгоды не даёт.

**Блоки и стрелки.** Блоки делаем расширением `shape` (новые `shapeType` + подпись), а
стрелку — новым объектом `connector` со ссылками на блоки. Отдельный тип `block` дублировал
бы существующие трансформации, выбор и хранение; свободные стрелки остаются текущим `shape`.

**Ластик.** Клиентский хит-тест + существующий `object_delete` (выбрано). Отдельное
серверное сообщение «erase» ничего не даёт: права и каскады всё равно проверяются на сервере.

## 7. Согласованные решения

- Ластик удаляет объекты целиком; учитель/админ — любые, ученик — свои.
- Блоки: процесс, решение, начало/конец; подпись внутри; без портов, стрелка цепляется за
  блок, на котором её начали и закончили; удаление блока удаляет его стрелки.
- Фрейм: привязка по положению (бросил внутрь — прикрепился, вытащил — открепился);
  фон — заливка, линии или клетка; дети двигаются с фреймом, не масштабируются; вложенных
  фреймов нет; удаление фрейма удаляет содержимое.
- Модель фрейма — вариант A (плоская, `frameId`, абсолютные координаты).

## 8. Модель объектов и протокол

### 8.1. Блоки схемы

`type: "shape"`, `shapeType` ∈ `process | decision | terminator`, плюс `content` (подпись,
может отсутствовать). Остальные поля — как у фигур: `x, y, width, height, color,
strokeWidth, fill`.

- Создание: `shape_add` с новым `shapeType` (схема расширяется). Подпись добавляется
  двойным кликом и сохраняется существующим `text_update`: сервер принимает цель, если это
  `text` **или** фигура с одним из трёх `shapeType`, и обновляет `content`. Broadcast остаётся
  `text_update` с полным объектом; клиент для блоков обновляет подпись.
- Рендер: процесс — прямоугольник, решение — ромб, начало/конец — скруглённый прямоугольник
  («стадион»). Подпись по центру, перенос по ширине, шрифт фиксированный 16 px.
- Поворот запрещён (Transformer отключает rotate для блоков, фреймов и коннекторов).
- Перемещение и изменение размера — существующими `object_update`/`object_transform`.

### 8.2. Стрелки-коннекторы

Новый объект `type: "connector"` c `fromId`, `toId`, `color`, `strokeWidth`. Позиции не
хранятся: линия считается по геометрии блоков.

- Создание: инструмент «Стрелка». Если нажатие началось на блоке схемы и отпущено на другом
  блоке — отправляется `connector_add {objectId, fromId, toId, color, strokeWidth}`; иначе
  создаётся обычная свободная стрелка (`shape_add`, как сейчас). Коннектор **не** добавляется
  локально оптимистично: сервер валидирует концы и рассылает `connector_add` всем, включая
  отправителя; клиент добавляет объект по событию.
- Сервер проверяет: оба блока существуют, оба — `shape` с блочным `shapeType`, в одной
  странице, не совпадают. Иначе `invalid_message`.
- Геометрия: центр-в-центр, обрезанная по границе блока (прямоугольник/ромб/скруглённый
  прямоугольник), наконечник у целевого блока; пересчёт при любом изменении
  `x/y/width/height` блока, при `frame_moved` и после загрузки снимка.
- Удаление блока удаляет все коннекторы с `fromId`/`toId` = блок.
- Коннектор нельзя двигать/масштабировать/поворачивать; его можно выбрать и удалить
  (автор/стафф); он участвует в хит-тесте ластика.

### 8.3. Фреймы

Новый объект `type: "frame"`:
`x, y, width, height`, `fill` (цвет или пусто), `pattern` ∈ `none | lines | grid`,
`stroke`, `strokeWidth`. Дети — обычные объекты с полем `frameId`.

- Создание: новый инструмент «Фрейм», протяжка как у фигуры; сообщение
  `frame_add {objectId, x, y, width, height, fill, pattern, stroke, strokeWidth}`.
  Новый фрейм попадает в самый низ слоя содержимого (под все объекты).
- Новый фрейм при создании **захватывает** уже лежащие в нём объекты (якорь: центр для
  фигур/картинок/блоков, левый верхний угол для текста), если у них ещё нет `frameId`.
  Сервер сообщает список захваченных `frame_captured {frameId, objectIds}` — событие
  получают все, включая создателя фрейма.
- Привязка при создании/перемещении/трансформации объекта: сервер сам вычисляет фрейм по
  якорю (центр/верхний левый угол) среди фреймов той же страницы и пишет `frameId` в объект;
  клиент это поле не присылает. Вне фрейма — `frameId` отсутствует. Клиент **зеркалит** то же
  вычисление локально (фреймы уже загружены), чтобы сразу двигать новым объектом вместе с
  фреймом; сервер остаётся авторитетным.
- Перемещение: на dragmove клиент двигает фрейм и его детей локально; на dragend отправляет
  `frame_move {frameId, x, y}` (x/y — новое положение фрейма). Сервер сдвигает фрейм и всех
  детей на ту же дельту, сохраняет и рассылает `frame_moved {frameId, x, y, children:
  [{id, x, y}]}` (всем, включая отправителя; абсолютные координаты идемпотентны).
- Изменение размера фрейма детей не двигает и привязку не пересчитывает. Поворот запрещён.
- Стиль фона: при выделении фрейма в тулбаре появляется панель: тип фона (нет/линии/клетка)
  и цвет заливки из палитры. Изменения — `frame_style {objectId, fill, pattern}`; сервер
  обновляет фрейм и рассылает событие. Линии/клетка рисуются серым по светлому фону,
  шаг 24 px; при заливке используется выбранный цвет.
- Удаление фрейма удаляет всех детей и коннекторы, привязанные к блокам-детям. Явное
  удаление (Delete) спрашивает подтверждение; ластик — без вопроса.
- Вложенность запрещена: фрейм не захватывает и не прикрепляется к другому фрейму.

### 8.4. Удаление и каскады

`object_delete` (клиент → сервер) расширяется правами: стафф или автор объекта. При удалении
сервер каскадно удаляет:

- коннекторы, у которых `fromId`/`toId` — удаляемый блок;
- для фрейма — всех детей (`frameId` = фрейм) и коннекторы, привязанные к блокам-детям.

Каждый удалённый объект рассылается отдельным `object_delete`; для каскада — **всем**,
включая инициатора (удаление идемпотентно). Обычное одиночное удаление по-прежнему
исключает отправителя (он уже удалил локально).

Права на фрейм: стафф удаляет любой; ученик — только свой фрейм и только если **все** его
дети принадлежат ему; иначе `forbidden`. Коннекторы чужих авторов, привязанные к его блоку,
удаляются вместе с блоком (иначе остаётся висячая стрелка).

### 8.5. Ластик

Инструмент «Ластик» больше не создаёт штрихи. На pointerdown/move он ищет объекты, которые
пересекает окружность радиуса `max(10, width * 1.5)` мировых единиц (штрихи и коннекторы —
расстояние до сегментов, остальные — пересечение с мировым bbox), фильтрует по праву удаления
(стафф/автор, для фрейма — правило выше) и удаляет локально, отправляя `object_delete` на
каждый. Фрейм ластик задевает **только по рамке** (полоса `strokeWidth + radius` вокруг
границы), а не по всей площади — иначе стирание ребёнка внутри фрейма удаляло бы весь фрейм.
Курсор — перекрестие; старые пиксельные штрихи ластика остаются объектами и могут быть
удалены как обычные.

## 9. Авторство локальных объектов

Сейчас локальные фигуры, текст и картинки создаются без `author`, поэтому ученик не может
двигать/трансформировать своё до перезагрузки. Исправление:

- `ToolManager` получает `getAuthor`; в локальные `stroke`/`shape` объекты добавляется
  `author: state.user.id`.
- `main.js` добавляет `author` в локальные `text`/`image` объекты.
- После вставки картинки доска переключается в режим «Выбор» и выделяет её, чтобы сразу
  можно было подвинуть.

Сервер по-прежнему сам проставляет автора в своих объектах; клиентское поле влияет только
на локальную проверку `canEditObject` до прихода подтверждения.

## 10. Фронтенд

- **Палитра:** к существующим инструментам добавляются «Процесс», «Решение», «Начало/конец»
  и «Фрейм» (иконки + подсказки, горячие клавиши `P`, `D`, `S`, `F`). Инструмент «Стрелка»
  при протяжке между блоками создаёт коннектор, иначе — свободную стрелку.
- **Board:** рендер новых типов (`process`, `decision`, `terminator`, `connector`, `frame`),
  паттерны фона, пересчёт коннекторов при изменениях блоков, drag-группа фрейма
  (`dragstart/dragmove/dragend`), каскадное локальное удаление, `eraseAt(point, radius)`,
  отключение трансформаций для коннекторов и поворота для блоков/фреймов, колбэк
  `onSelectObject(id)` — по нему main показывает/прячет панель фрейма.
- **Редактор подписи:** двойной клик по блоку открывает существующий `#text-editor` с текущей
  подписью; сохранение отправляет `text_update`. Для фрейма двойной клик не открывает текст.
- **Панель фрейма:** `#frame-panel` в тулбаре (скрыта, пока не выбран редактируемый фрейм):
  кнопки «Нет / Линии / Клетка» и палитра заливки; изменения уходят `frame_style`.
- **Удаление:** Delete/Backspace — как сейчас только для стаффа; для фрейма confirm
  «Удалить фрейм и всё содержимое?». Ученик удаляет свои объекты ластиком.
- **События:** новые `connector_add`, `frame_add`, `frame_captured`, `frame_moved`,
  `frame_style` обрабатываются как добавление/обновление объектов с фильтрацией по странице.

## 11. Сервер, Redis и хранение

- Схемы: `ShapeAdd.shapeType` + три значения; `ConnectorAdd`, `FrameAdd`, `FrameMove`,
  `FrameStyle`, `FrameCaptured`; `TextUpdate` для блоков. `client_message_adapter` расширяется.
- `_handle_shape_add`/`_handle_connector_add`/`_handle_frame_add` проверяют страницу, лимит
  объектов, дубликаты; для фрейма — захват существующих объектов и `frame_captured`.
- `_handle_object_update`/`_handle_object_transform` пересчитывают `frameId` по якорю;
  broadcast несёт `frameId`, чтобы клиенты обновили привязку (для движения фрейма это не
  требуется).
- `_handle_frame_move`: дельта по старому `x/y`; сдвиг детей; broadcast `frame_moved`;
  Redis-состояние обновляется для фрейма и детей; `_apply_remote_event` делает то же на
  других инстансах.
- `object_delete`: права автор/стафф, каскады, удаление из `room.index`/`objects` и Redis.
- Новые события добавляются в `WORKSPACE_SCOPED_EVENTS`/`ADD_EVENTS` по смыслу; снимок
  SQLite хранит новые поля без миграции схемы (JSON объектов).
- Лимит объектов на комнату остаётся общим; фрейм/коннектор считаются объектами.

## 12. Тесты

**Backend:**
- Схемы: новые shapeType, connector/frame сообщения, валидация коннектора (концы — блоки на
  той же странице), запрет лишних полей.
- Блок: добавление, подпись через `text_update`, ограничение длины/пустоты.
- Коннектор: создание, удаление блока каскадом, удаление коннектора, права.
- Фрейм: создание и захват существующих объектов, `frame_move` сдвигает детей, `frame_moved`
  в broadcast/Redis, изменение стиля, удаление каскадом (дети + коннекторы), запрет ученику
  удалять фрейм с чужими детьми, вложенность не создаётся.
- Удаление: ученик удаляет свой объект, но не чужой; стафф — любой.
- Персистентность: снимок с `frameId`, коннекторами и фреймами восстанавливается; Redis
  синхронизирует `frame_moved`/`frame_captured` между менеджерами.

**E2E:**
- Картинка ученика двигается сразу после вставки (RED на текущем коде) и остаётся на месте
  после reload.
- Ластик удаляет штрих, фигуру, текст, картинку, блок и фрейм; у ученика не удаляет чужое;
  удаление блока убирает его стрелки; удаление фрейма убирает содержимое.
- Блоки: создание трёх типов, подпись двойным кликом и её изменение, стрелка между блоками
  следует за перемещением и изменением размера, удаление блока убирает стрелку, свободная
  стрелка по-прежнему работает.
- Фреймы: создание, фон (заливка/линии/клетка), бросок элемента внутрь прикрепляет,
  перемещение фрейма двигает детей, вытаскивание открепляет, изменение размера не двигает
  детей, удаление с подтверждением убирает содержимое.
- Регресс существующих сценариев (страницы, перенос, права, reconnect, mobile).

## 13. Мои решения (проверить при чтении)

1. Блоки и фреймы — расширение существующей плоской модели; отдельного слоя/групп нет.
2. Подпись блока — поле `content`, редактируется существующим `text_update`; шрифт 16 px,
   перенос по ширине, поворот блока/фрейма запрещён.
3. Стрелка-коннектор не хранит координаты и всегда пересчитывается по геометрии блоков;
   свободные стрелки остаются `shape`.
4. Привязка к фрейму вычисляется сервером по якорю (центр для фигур/картинок/блоков, левый
   верхний угол для текста); клиент `frameId` не присылает.
5. Новый фрейм захватывает уже лежащие внутри объекты без `frameId`; изменение размера
   фрейма привязку не пересчитывает.
6. Удаление фрейма удаляет детей и их коннекторы; ученик может удалить только свой фрейм,
   если все дети его; иначе отказ.
7. Удаление объекта разрешено автору или стаффу (нужно для ластика ученика); Delete-клавиша
   в UI остаётся стаффовой, ученик удаляет ластиком.
8. Ластик — окружность радиуса `max(10, width*1.5)`; штрихи проверяются по расстоянию до
   сегментов, остальные по bbox.
9. Старые пиксельные штрихи ластика не мигрируются и не удаляются автоматически; рендерятся
   как раньше.
10. После вставки картинки включается «Выбор» и картинка выделяется.

## 14. Что остаётся строителю

- Точная геометрия пересечения луча с ромбом/скруглённым прямоугольником и формула якоря
  для текста (левый верхний угол) — в плане.
- Раскладка новых кнопок/панели фрейма в тулбаре и на мобильном.
- Сигнатуры Board/ToolManager (`eraseAt`, `getAuthor`, drag-группа фрейма) и порядок
  обработки каскадов.
- Разбиение на задачи и порядок реализации — в плане.
