# Учётные записи, роли и комнаты учителей — дизайн

Дата: 2026-11-16. Итерация после «воркспейсов».

## 1. Зачем

Сейчас доска не знает, кто на ней рисует: `POST /api/login` принимает любое имя, роль
и общий код учителя, выдаёт JWT на 12 часов и случайный `user_id` при каждом входе.
Комната — это строка `room_id` из ссылки, создаётся неявно при первом входе; владельца,
названия и списка доступа у неё нет. Из-за этого нельзя ни закрепить комнату за учителем,
ни пустить в неё только своих учеников, ни отозвать доступ.

Итерация вводит полноценные УЗ, три роли, регистрацию с подтверждением администратором и
комнаты, принадлежащие учителю, с выдачей доступа конкретным ученикам.

## 2. Цели

1. Роли: ученик, учитель, администратор. Администратор = функционал учителя + управление УЗ
   + доступ ко всем комнатам.
2. Регистрация по имени, логину и паролю. Все регистрируются учениками; до подтверждения
   администратором сайт недоступен.
3. Учителей назначает только администратор. Администратор создаётся при первом запуске.
4. Комната — постоянная сущность: уникальный `id`, название, владелец-учитель. Учитель
   создаёт, переименовывает и удаляет свои комнаты, выдаёт и отзывает доступ ученикам.
5. Ученик видит и открывает только комнаты, куда его добавили. Гостевого входа нет.
6. Доступ проверяется на сервере при каждом REST-запросе и при каждом WS-подключении;
   отзыв доступа и блокировка выкидывают из комнаты сразу.
7. Сессии — серверные, в HttpOnly-cookie. Токенов в URL и localStorage нет.

## 3. Не-цели

- Самостоятельная смена пароля, восстановление по email, 2FA, OAuth.
- Регистрация на учителя/администратора, несколько администраторов через интерфейс
  (второго админа можно назначить только в БД; bootstrap-админ защищён).
- Расписание уроков, срок действия доступа, со-учителя, передача комнаты другому учителю.
- Живое обновление списка комнат/заявок без перезагрузки (обновление по фокусу и кнопке).
- Аудит действий администратора.
- Миграция старых анонимных досок — старые снимки удаляются.
- Нагрузочное тестирование (решение: отказываемся на этом этапе).

## 4. Анти-цели

- Вход без аккаунта, общий код учителя, доступ к комнате по одному знанию ссылки.
- Токен/пароль в URL, localStorage, sessionStorage или логах.
- Роль, зашитая в клиентское состояние и не перепроверяемая в БД.
- Неявное создание комнаты при подключении.

## 5. Ограничения

- FastAPI + сырой SQLite (без ORM и Alembic), ванильный JS-фронт, WebSocket-протокол,
  `RoomManager`, снимки в SQLite, Redis для живого состояния, Caddy в проде.
- Python 3.13: `bcrypt` ставится колесом, argon2-cffi не берём.
- Тесты — pytest (+ `TestClient`, `fakeredis`, `moto`) и Playwright.
- Один процесс/несколько инстансов с общим Redis: сессии и УЗ живут в SQLite (общий файл),
  поэтому проверка статуса работает на любом инстансе; «выкинуть» — через существующий
  механизм kick с Redis-ретрансляцией.

## 6. Рассмотренные подходы

**A. Bearer JWT, как сейчас** (`sessionStorage`, `?token=` для WS, проверка статуса в БД на
каждом запросе). Меньше правок, но токен виден в логах и истории, отзыв не действует на уже
открытый WS без отдельных событий, logout чисто клиентский.

**B. Серверные сессии в HttpOnly-cookie (выбран).** Вход ставит случайный id сессии;
каждый REST-запрос и WS-хендшейк читает cookie, грузит пользователя из SQLite и проверяет
статус/роль. Logout удаляет сессию, блокировка и смена роли действуют сразу, WS авторизуется
cookie без токена в URL. Цена: переписать проверку входа и WS-хендшейк, добавить таблицу
сессий, закрыть CSRF (SameSite=Lax + проверка Origin + JSON-тело).

Остальное (таблицы УЗ/комнат/доступа, роли, дашборды, проверка прав) одинаково для обоих.

## 7. Решения, согласованные с заказчиком

- Вход без аккаунта больше не поддерживается.
- Доступ к комнате выдаёт учитель; ученик открывает только выданные комнаты.
- Все регистрируются учениками; учителя назначает администратор; администратора создаём
  при первом запуске.
- Администратор имеет доступ ко всем комнатам.
- Старые снимки анонимных комнат удаляем, миграции данных нет.
- Нагрузочные тесты из процесса исключаем.
- Сессии — вариант B (HttpOnly-cookie).

## 8. Домен и данные

Один SQLite-файл (`DATA_DIR/whiteboard.db`), новые таблицы создаёт
`app/services/accounts.py` (класс `AccountStore`, все запросы через `asyncio.to_thread`,
как в `SnapshotStore`).

```sql
CREATE TABLE IF NOT EXISTS users (
  id            TEXT PRIMARY KEY,              -- u_<16 hex>
  login         TEXT NOT NULL,                 -- как ввёл пользователь
  login_norm    TEXT NOT NULL UNIQUE,          -- lower(trim(login))
  name          TEXT NOT NULL,                 -- 1..40, схлопнутые пробелы
  password_hash TEXT NOT NULL,                 -- bcrypt
  role          TEXT NOT NULL DEFAULT 'student'
                CHECK (role IN ('student','teacher','admin')),
  status        TEXT NOT NULL DEFAULT 'pending'
                CHECK (status IN ('pending','active','blocked','rejected')),
  color         TEXT NOT NULL,                 -- pick_color(id)
  created_at    TEXT NOT NULL,
  updated_at    TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS rooms (
  id         TEXT PRIMARY KEY,                 -- r_<16 hex>
  name       TEXT NOT NULL,                    -- 1..80 после trim
  owner_id   TEXT NOT NULL REFERENCES users(id),
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS rooms_owner_idx ON rooms(owner_id);

CREATE TABLE IF NOT EXISTS room_access (
  room_id    TEXT NOT NULL REFERENCES rooms(id) ON DELETE CASCADE,
  user_id    TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  granted_by TEXT NOT NULL,
  created_at TEXT NOT NULL,
  PRIMARY KEY (room_id, user_id)
);

CREATE TABLE IF NOT EXISTS sessions (
  id         TEXT PRIMARY KEY,                 -- secrets.token_urlsafe(32)
  user_id    TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  created_at TEXT NOT NULL,
  expires_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS sessions_user_idx ON sessions(user_id);

CREATE TABLE IF NOT EXISTS app_meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);
```

`AccountStore` открывает соединение с `PRAGMA foreign_keys=ON`; удаления комнат/пользователей
всё равно делает явно, чтобы не зависеть от каскадов.

### Статусы пользователя

`pending` (после регистрации) → `active` (подтверждён администратором) или `rejected`
(отклонён; повторно подать заявку тем же логином нельзя, администратор может передумать).
`active` ⇄ `blocked`. Войти и открыть WS можно только со статусом `active`.

### Bootstrap-администратор

Настройки `ADMIN_LOGIN` (по умолчанию `admin`), `ADMIN_PASSWORD` (по умолчанию
`admin-change-me`, в лог при старте пишется предупреждение, если пароль дефолтный),
`ADMIN_NAME` (по умолчанию `Администратор`). При старте: если в таблице нет ни одного
пользователя с ролью `admin` — создать активного администратора с хешем пароля.
Существующего администратора env-переменные не перезаписывают. Сменить пароль можно через
админский сброс пароля самому себе. Заблокировать, понизить или удалить администратора
нельзя (400) — включая себя.

### Правила доступа к комнате

Доступ разрешён, если:

- роль `admin`; или
- пользователь — владелец комнаты и его роль `teacher`; или
- в `room_access` есть запись `(room_id, user_id)` и пользователь `active`.

Выдавать доступ можно только активным ученикам; строка `room_access` не зависит от будущей
роли (если ученика повысили до учителя, выданный доступ продолжает работать). Владелец и
администратор в `room_access` не нуждаются.

Если владельца понизили до ученика или заблокировали, его комнаты остаются в базе, он в них
не входит; администратор видит их в общем списке и может удалить. Передачи комнаты другому
учителю в этой итерации нет.

## 9. Аутентификация и сессии

- `POST /api/register {login, name, password}` → 201 `{status: "pending"}`;
  занятый логин → 409 `{detail: {code: "login_taken", message: ...}}`.
- `POST /api/login {login, password}` → 200 `{user, permissions}` + `Set-Cookie: wb_session=...`;
  неверная пара → 401 `invalid_credentials`; `pending`/`rejected`/`blocked` → 403 с
  `detail.code` = `pending` / `rejected` / `blocked` и человекочитаемым текстом (cookie не
  ставится).
- `POST /api/logout` → 204, сессия удаляется из БД, cookie стирается.
- `GET /api/me` → 200 `{user, permissions}` или 401; используется при загрузке SPA и после
  переподключения.
- Cookie: имя `wb_session`, `HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` из настройки
  `COOKIE_SECURE` (в проде `true`), `Max-Age = SESSION_TTL_HOURS` (по умолчанию 12).
- Сессии в SQLite; просроченные удаляются при старте и при каждом логине. Logout удаляет
  только текущую сессию; сброс пароля и блокировка удаляют все сессии пользователя.
- Пароли: bcrypt (cost 12), длина 8…72 байта (ограничение bcrypt), без обрезки пробелов.
  Пароль никогда не логируется.
- Логин: `^[a-zA-Z0-9_.-]{3,32}$`, хранится нормализованным (lower, trim); вход
  регистронезависимый. Имя: 1…40 после схлопывания пробелов.
- CSRF: для всех не-GET REST-запросов зависимость проверяет `Origin` (или `Referer`, если
  Origin нет) — хост должен совпадать с хостом запроса; тело только JSON. Cross-site
  WebSocket cookie не получит из-за SameSite=Lax.
- Простое ограничение перебора: не более 10 неудачных логинов и 5 регистраций в минуту с
  одного IP (in-memory, ключ — `request.client.host`), ответ 429. Ограничение честно работает
  за Caddy только при включённых proxy headers (в uvicorn они включены по умолчанию для
  127.0.0.1).
- JWT полностью убираем (`services/auth.py` сокращается до хеширования пароля и генерации
  id сессии; `jwt_secret`/`jwt_ttl_hours`/`TEACHER_CODE` удаляются из настроек).

## 10. Права

`permissions_for(role)`:

| | student | teacher | admin |
|---|---|---|---|
| canDraw | + | + | + |
| canClear | – | + | + |
| canDelete | – | + | + |
| canManageUsers (kick в комнате) | – | + | + |
| canManageWorkspaces | – | + | + |
| canCreateRooms | – | + | + |
| canManageAccounts | – | – | + |

В WS-обработчиках проверка «учитель» меняется с `role != "teacher"` на
`role not in ("teacher", "admin")` (общий хелпер `is_staff`). `TokenPayload.is_teacher`
заменяется полем роли из БД.

## 11. REST API

Все ответы — JSON; ошибки — `{detail: {code, message}}` (для auth/admin/rooms). Активная
сессия обязательна везде, кроме `/api/register` и `/api/login`; `/health*`, `/metrics`,
`/api/upload` — как сейчас (`upload` требует активную сессию).

**Аутентификация:** `POST /api/register`, `POST /api/login`, `POST /api/logout`,
`GET /api/me` — см. раздел 9.

**Комнаты (текущий пользователь):**

- `GET /api/rooms` — ученик: выданные комнаты `[{id, name, owner: {id, name}}]`;
  учитель/админ: свои комнаты с тем же форматом.
- `GET /api/rooms/all` — только админ: все комнаты с владельцем.
- `GET /api/rooms/{id}` — комната, если доступ разрешён (для шапки доски и deep-link);
  иначе 403/404.
- `POST /api/rooms {name}` — учитель/админ создаёт свою комнату, 201; id генерирует сервер
  (`r_<16 hex>`); имя 1…80.
- `PATCH /api/rooms/{id} {name}` — владелец или админ; 204.
- `DELETE /api/rooms/{id}` — владелец или админ; 204. Удаляет строку комнаты, доступы,
  снимок из SQLite и live-состояние в Redis, выкидывает всех участников с причиной
  «Комната удалена». Удаление рассылает по Redis `remote_room_closed`: каждый инстанс
  закрывает свою копию комнаты (без сохранения снимка) и выкидывает локальных участников.
  Порядок: сначала рассылка и закрытие, затем удаление строки комнаты, доступов, снимка и
  ключей Redis. Даже если гонка сохранит снимок после удаления, комната уже недоступна (нет
  строки `rooms`), а снимок вычистится по `ROOM_TTL_DAYS`.
- `GET /api/rooms/{id}/access` — владелец или админ: `[{user: {id, name, login}}]`.
- `PUT /api/rooms/{id}/access {userIds: [...]}` — владелец или админ; полная замена списка;
  неактивные/несуществующие id → 400 `invalid_user`; добавленные получают доступ сразу,
  удалённые — выкидываются из комнаты (если были внутри) с причиной «Учитель отменил доступ
  к комнате». Ответ 200 с новым списком.

**Каталог учеников для выдачи доступа:** `GET /api/users?role=student&status=active&q=...` —
доступен учителю и админу, возвращает только `{id, name, login}`; `q` ищет по имени и логину
(contains, до 50 результатов). Полные данные УЗ учителю не отдаются.

**Администрирование УЗ (только admin):**

- `GET /api/admin/users?status=&role=&q=` — все УЗ, заявки первыми, затем по дате создания;
  поля `{id, login, name, role, status, createdAt}`.
- `PATCH /api/admin/users/{id} {status?, role?}` — статусы `active|blocked|rejected`,
  роли `student|teacher`; `pending → active` — это подтверждение. Смена роли на `teacher` —
  назначение учителем. Блокировка и смена роли удаляют сессии пользователя и выкидывают его
  из всех комнат. Администратора менять нельзя (400).
- `POST /api/admin/users/{id}/password {password}` — сброс пароля (в том числе своего),
  удаляет все сессии пользователя.

**Загрузка изображений:** без изменений, но с cookie-сессией.

## 12. WebSocket

`/ws/{room_id}` без query-токена; cookie `wb_session` читается из `websocket.cookies`.

Порядок проверок: комната есть в БД (иначе close 4404 `room_not_found`) → сессия валидна и
пользователь `active` (4401 `unauthorized`) → доступ к комнате (4403 `forbidden`). Только
после этого `manager.join`. Неявного создания комнат больше нет.

Роль и права в комнате берутся из БД при подключении; для админа — права учителя. Правила
страниц/объектов/курсоров не меняются. Существующие коды закрытия сохраняются (`4400`
некорректный id, `4409` сессия заменена), `4403 room_mismatch` больше не используется.

Выкидывание по событиям (отзыв доступа, блокировка, смена роли, удаление комнаты)
использует существующий `RoomManager.kick` / `_kick_local` (Redis `remote_kick` для чужих
инстансов): клиент получает `kicked` с причиной, сокет закрывается, SPA возвращается на
дашборд. Удаление комнаты дополнительно рассылает `remote_room_closed` (раздел 11), чтобы
инстансы убрали живую копию комнаты, не дожидаясь опустения.

## 13. Фронтенд

Один `index.html`, четыре состояния (секции + `hidden`):

1. **Вход/регистрация.** Логин, пароль; на регистрации ещё имя. Роль и код учителя убраны.
   Ошибки: неверная пара, «заявка на рассмотрении», «заявка отклонена», «заблокирована».
2. **Статус заявки.** Если вход отклонён из-за статуса: текст и кнопка «Вернуться ко входу».
3. **Дашборд.**
   - Ученик: список выданных комнат (название, учитель) + «Открыть».
   - Учитель: свои комнаты (название, «Открыть», «Переименовать», «Доступ», «Удалить»),
     «Создать комнату».
   - Админ: вкладки «Комнаты» (все комнаты с владельцем, открыть/удалить) и «Пользователи»
     (заявки: подтвердить/отклонить; остальные: роль, блокировка/разблокировка, сброс
     пароля), плюс свои комнаты как у учителя.
   - Обновление списков по кнопке и при возврате фокуса на окно.
4. **Комната.** Шапка: название комнаты, «Выйти из комнаты» (в дашборд), «Выйти» (logout).
   Доска и панели как сейчас. Deep-link `/?room=<id>` открывает комнату после проверки
   доступа; без доступа — сообщение и дашборд. Администратор отображается в списке
   участников с бейджем «администратор».

`SyncClient`: без токена, cookie отправляется браузером; `FATAL_MESSAGES` дополняется
кодами 4401 («Сессия истекла — войдите снова», возврат на экран входа), 4403 («Нет доступа к
комнате», возврат на дашборд), 4404 («Комната не найдена», дашборд); после фатального
закрытия — дашборд. `sessionStorage` больше не хранит сессию/токен: там остаётся только
несекретное состояние UI `{roomId, workspaceId}`, чтобы после reload открыть ту же страницу
доски; `?workspace=` остаётся. Logout доступен с дашборда: из комнаты сначала выходим в
дашборд, затем сессия удаляется.

## 16. Тесты

**Unit:** нормализация логина, bcrypt-хеш/проверка, генерация id, права по ролям, правила
доступа (admin / owner-teacher / grant), bootstrap-админ (создаётся один раз, env не
перезаписывает), миграционный маркер, отказ менять администратора.

**REST-интеграция:** регистрация → pending → login 403 → approve → login 200 → `/api/me`;
занятый логин; неверный пароль; blocked/rejected; cookie-атрибуты; logout; истёкшая сессия;
CSRF (чужой Origin); троттлинг; `GET /api/rooms` для трёх ролей; CRUD комнат и права
(чужой учитель не переименует/не удалит); выдача/отзыв доступа; каталог учеников; админские
эндпоинты и их запрет для учителя/ученика; блокировка/смена роли/сброс пароля убивают сессии.

**WS-интеграция:** без cookie 4401; pending/blocked 4401; нет доступа 4403; нет комнаты
4404; доступ выдан — подключается и рисует; отзыв доступа выкидывает; блокировка выкидывает;
админ входит в чужую комнату и имеет права учителя; понижение учителя выкидывает и лишает
прав после переподключения; `workspace`-параметр работает по-прежнему.

**E2E (Playwright):** регистрация + ожидание + подтверждение админом + вход; ученик видит
только выданные комнаты; учитель создаёт/переименовывает/удаляет комнату и выдаёт доступ;
отзыв доступа выкидывает ученика; ученик не может очищать/удалять/управлять страницами;
основной урок (рисование, курсор, reload); страницы и перенос (существующие сценарии на
новой авторизации); админская панель (подтверждение, повышение до учителя, блокировка);
reconnect; мобильный viewport; deep-link без доступа.

Старые тесты, логинившиеся кодом учителя, переписываются на фикстуры «админ/учитель/ученик
через регистрацию и подтверждение» (REST-хелперы в `conftest`/`helpers`).

## 17. Мои решения (можно оспорить при чтении)

1. bcrypt cost 12; пароль 8…72 байта; логин 3…32, `[a-zA-Z0-9_.-]`, регистронезависимый.
2. Админский сброс пароля включён (в том числе своего) — иначе bootstrap-пароль не сменить;
   самостоятельная смена пароля пользователем — не в этой итерации.
3. Комнату можно переименовать и удалить; удаление выкидывает участников и чистит снимок,
   доступы и Redis.
4. Выдача доступа — полная замена списка (`PUT`), а не построчные `POST/DELETE`.
5. Учитель видит каталог активных учеников (имя+логин, до 50) для выдачи доступа.
6. Заблокированный/понижённый учитель теряет и сессии, и комнаты (комнаты остаются в БД,
   ими управляет админ); передачи комнаты нет.
7. Список комнат на дашборде обновляется по кнопке и фокусу, без realtime.
8. Ограничение перебора — простое in-memory на IP, без Redis.
9. `?room=<id>` остаётся для deep-link; знание ссылки без доступа ничего не даёт.
10. Сессии фиксированные 12 часов, без продления; cookie `Secure` из конфига.
